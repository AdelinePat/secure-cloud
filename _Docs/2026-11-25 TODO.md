What to work on first

1. Key distribution for E2EE, done before or alongside file/. It's your project's core promise ("the server must never access the plaintext"). Right now the app can't let two people actually talk. File encryption will need the same mechanism, so if you build file/ first you'll design it twice. A minimal version:
   - Each client generates an identity keypair (IdentityKeyStore already exists) and uploads its public key to auth.
   - The conversation creator generates a random conversation key and encrypts a copy of it for each participant's public key. Messaging stores these encrypted copies per participant.
   - Clients fetch their copy and decrypt it with their private key.
2. file/ service plus the gateway /files routes. It reuses the JWT check, repository and audit pieces that messaging already has.
3. User registration (POST /users) in auth and the client. It's small, but without it a demo only works with seeded users.
4. Make messaging concurrent. Moving it to the async Beast session pattern the gateway already uses would also clean up the duplicated JWT-parsing blocks. Do it before demoing with several clients.
5. TLS at the gateway. Doing just the client↔gateway connection, using the existing certs, is enough for an MVP.

WebSockets, presence, logout/revocation, GET /conversations/{id}, deleting or leaving a conversation, and history pagination can wait until after the MVP. The client can poll history for now.

If you only have time for one thing, do item 1. A secure messaging app where the recipient can't decrypt the messages isn't functional yet.
